## 概述：电路交换、分组交换与性能

本讲共 7 道题：3 道带数值的例题、4 道讨论题。下面逐题给出**完整题干**与**详细解法**。

### Q1. 电路交换与分组交换分别能支持多少用户？

**原题（课件原文）**：Packet switching versus circuit switching — example：

- 链路带宽 1 Gb/s；
- 每个用户：活跃（active）时需 100 Mb/s，活跃时间占 10%；
- 图中 N 个用户共享这条 1 Gbps 链路。

> Q: how many users can use this network under circuit-switching and packet switching?

**解**：

1. **电路交换**：用户一旦通话就固定占用 100 Mb/s 的电路，链路总带宽 1 Gb/s = 1000 Mb/s，因此最多支持

```
N = R / r = 1000 / 100 = 10 个用户
```

2. **分组交换**：用户只有 10% 的时间活跃，同一时刻的活跃用户数 X 服从二项分布 B(n, 0.1)，n 为用户总数。
3. 链路能同时容纳 10 个活跃用户（每个 100 Mb/s）。当 n = 35 时，期望活跃数 E(X) = 35 × 0.1 = 3.5，而 P(X > 10) < 0.0004——"超载"概率不到万分之四，工程上可以接受。
4. 所以分组交换在同样链路下可接约 35 个用户，是电路交换的 3.5 倍。

**答**：电路交换 **10 个**；分组交换约 **35 个**（同时活跃超过 10 个的概率 < 0.0004）。结论：**突发型业务用分组交换，恒定速率业务（语音）用电路交换**。

### Q2. 车队在第二个收费站前排好队需要多久？

**原题（课件原文）**：Caravan analogy —

- 车 ~ 比特（bit），车队 ~ 分组（packet），收费站服务 ~ 链路传输；
- 收费站服务一辆车需 **12 s**（相当于一个比特的发送时间）；
- 车队以 **100 km/h** "传播"；
- 两个收费站相距 **100 km**，车队共 **10 辆车**（相当于 10 bit 的分组）。

> Q: How long until caravan is lined up before 2nd toll booth?

**解**：

1. 把整个车队"推"出第一个收费站：10 辆车 × 12 s = 120 s = **2 min**（相当于 10 bit 分组的**发送时延**）。
2. 最后一辆车从第一站传播到第二站：100 km ÷ 100 km/h = **1 h = 60 min**（相当于**传播时延**）。
3. 两者相加：2 + 60 = **62 min**。

**答**：**62 分钟**。这道题的意义：发送时延和传播时延是两个独立的部分，量级可以差很多。

### Q3. 第一辆车会不会在所有车服务完之前到达第二个收费站？

**原题（课件原文）**：仍用上面的车队模型，但改成：

- 车的"传播"速度变为 **1000 km/h**；
- 收费站服务一辆车变为 **1 min**。

> Q: Will cars arrive to 2nd booth before all cars serviced at first booth?

**解**：

1. 第一辆车出站：**1 min**。
2. 第一辆车从第一站到第二站：100 km ÷ 1000 km/h = **6 min**。
3. 所以第 **7 min** 时，第一辆车已到达第二站。
4. 此时第一个收费站才服务完 7 辆车（第 1～7 辆），**还有 3 辆车没服务**。

**答**：**会**。7 分钟后第一辆车已到第二站，第一站还剩 3 辆车。说明当"传播"很快、"服务"很慢时，后面的车还没发完，前面的车已经到了——这正是流水线/分组交换里"发送时延 > 传播时延"的情形。

### Q4. 如何把端系统接入边缘路由器？

**原题（课件原文）**：

> Q: How to connect end systems to edge router?

**解**：按使用场景分三类接入网：

1. **住宅接入（residential access nets）**：DSL（电话线）、HFC（有线电视同轴电缆）、FTTH/FTTR（光纤到户/到房间）。
2. **机构接入（institutional access networks）**：学校、公司，通常是以太网交换机 + WiFi + 边界路由器。
3. **移动接入（mobile access networks）**：WiFi、4G/5G 蜂窝。

**答**：住宅接入、机构接入、移动接入三类；每类的代表技术见上。

### Q5. 分组交换能不能提供"像电路交换一样"的行为？

**原题（课件原文）**：

> Q: How to provide circuit-like behavior with packet-switching?

**解**：

1. 分组交换靠**统计复用**，不预留资源，所以天生**不能保证**带宽、时延、不丢包。
2. 要"像电路交换"，只能在分组交换之上**加机制**：资源预留、准入控制、QoS 调度（优先级/加权公平）、流量工程、拥塞控制等。
3. 课件原话是"**It's complicated**"——只能说"尽量像"，不能真正等价；后续课程会讲各种"让分组交换尽量接近电路交换"的技术。

**答**：很难；需要资源预留、准入控制、QoS 调度、流量工程等手段来逼近，但无法真正保证。

### Q6. 电路交换（预留资源）与分组交换（按需分配）各举一个生活类比。

**原题（课件原文）**：

> Q: human analogies of reserved resources (circuit switching) versus on-demand allocation (packet switching)?

**解**：

- **电路交换 = 预留资源**：包场、提前订座、专车、包机——先把资源占住，别人不能用。
- **分组交换 = 按需分配**：自助餐、排队打车、拼车、公共图书馆——谁有需求谁用，空闲时大家共享。

**答**：包场/订座 vs 自助餐/排队打车；核心区别是"**先占住**"还是"**用时才占**"。

### Q7. 除了"问时间"，还能举出哪些"人类协议"？

**原题（课件原文）**：

> Q: other human protocols?（课件用"Hi / Got the time? / 2:00"类比 TCP 的三次交互）

**解**：人类协议的特点也是"**有固定的报文格式、顺序和动作**"：

- **握手**：见面伸手 → 对方伸手 → 握住；
- **问路**："请问××怎么走？" → "往前走两个路口"；
- **点餐**："我要这个" → "好的，稍等"；
- **打电话**："喂" → "在" → 说正事；
- **寄信**：写地址 → 贴邮票 → 投递 → 对方签收。

**答**：握手、问路、点餐、打电话、寄信等；共同点是都有约定的格式、次序和响应动作。

### Q8. 如何查出计算机的 MAC 地址？有多少种方法？

**解**：MAC 地址是网卡的硬件地址（48 位，通常写成 `xx-xx-xx-xx-xx-xx`）。至少有 6 种方法：

1. **图形界面**：Windows「控制面板 → 网络和共享中心 → 更改适配器设置 → 双击网卡 → 详细信息 → 物理地址」；macOS「系统设置 → 网络 → 高级 → 硬件 → MAC 地址」。
2. **`ipconfig /all`**（Windows）：输出每个适配器的"物理地址"字段。
3. **`getmac`**（Windows）：直接列出所有网卡的 MAC。
4. **`ifconfig` / `ip link`**（Linux/macOS）：`ifconfig` 的 `ether` 字段，或 `ip link show` 的 `link/ether`。
5. **`arp -a`**：查看 ARP 缓存，能看到本机通信过的"IP → MAC"映射（不是本机自己的 MAC，但能查到对端 MAC）。
6. **抓包工具**：Wireshark 抓一帧，看以太网首部的 **Source MAC**；或读注册表 `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4D36E972-...}`、`wmic nic get name,macaddress`。

**注意**：一台机器可能有多块网卡（有线、无线、虚拟网卡），每块 MAC 不同；要分清问的是哪一块。

**实验方案**：

- **目的**：掌握查看 MAC 的多种方法，理解 MAC 与 IP 的区别；
- **环境**：一台 Windows 或 Linux 主机；
- **步骤**：依次执行 `ipconfig /all`、`getmac`、`arp -a`，再用 Wireshark 抓一个 ping 包看源 MAC；
- **结果与分析**：对比各方法得到的是否一致，说明"MAC 是链路层地址、IP 是网络层地址"；
- **总结**：MAC 全球唯一、烧在网卡里，IP 是逻辑地址、可随网络变化。

### Q9. 分别测量到几个国内、国外网站的性能，并做对比分析。

**解**：按"**工具 → 指标 → 对比 → 结论**"四步做。

1. **选目标**：国内 3 个（如 baidu.com、qq.com、163.com），国外 3 个（如 google.com、github.com、bbc.com）。
2. **测指标**（每个目标重复 10 次取平均）：
   - `ping 域名`：平均 RTT、丢包率、抖动；
   - `tracert` / `traceroute 域名`：跳数、每跳时延、是否经过国际出口；
   - `curl -o /dev/null -w "%{time_total}"` 或 `iperf3`：下载时间/吞吐。
3. **对比**：把国内、国外的 RTT、跳数、丢包率、吞吐列成表。
4. **分析**：
   - 国外站 RTT 明显更大（跨洋光缆 + 国际出口排队）；
   - 跳数更多，且中间会出现国际出口路由器；
   - 国内站若接了 CDN，RTT 小、路径短；
   - 丢包多出现在国际出口或对端入口。

**实验方案要点**：记录时间、网络环境（校园网/家宽）、是否用 VPN；用同一台机器、同一时间段测，减少误差。

### Q10. 如果访问某个网站特别慢，分析可能的原因，最好找实例做实验测试。

**解**：按"**从近到远、从下到上**"的顺序排查，每一步都有对应命令：

1. **DNS 层**：`nslookup 域名`、`dig 域名` 看解析时间与结果；换公共 DNS（8.8.8.8 / 114.114.114.114）对比。若"IP 能通、域名不通"，就是 DNS 问题。
2. **本地/接入网**：`ping 网关`、`ping 8.8.8.8`，看是否本地丢包、WiFi 信号差、带宽被占满。
3. **路径层**：`traceroute 域名`，看哪一跳时延突增（国际出口、对端入口、某运营商互联点）。
4. **丢包/重传**：`ping -n 100` 看丢包率；丢包会让 TCP 反复重传、吞吐骤降。
5. **服务器/应用**：换 URL、换时间段、换设备测试；`curl -w` 分段看 DNS、连接、TLS、首字节、下载各阶段耗时。
6. **其他**：MTU/分片、TLS 握手慢、CDN 未命中、浏览器插件/代理。

**实例（可写进作业）**：访问某国外站点慢 →

```
ping：RTT 250 ms、丢包 3%
traceroute：第 8 跳（国际出口）时延从 20 ms 跳到 200 ms
curl -w：DNS 20 ms、TCP 连接 260 ms、TLS 500 ms、首字节 800 ms、下载 5 s
```

结论：**主要是跨洋 RTT 大 + 国际出口拥塞**，不是本地或服务器问题；可用 CDN/代理/就近节点缓解。

## 应用层与覆盖网：RON、CDN、P2P

**本讲原题（课件原文）**：

> **课堂讨论**：RON 与公平：如果许多人都搭建 RON，会怎么样？
>
> **课堂练习**：（尽量）不看 sky computing 的论文，尝试设计一个 sky computing 的体系架构。
>
> **问题**：如果 Chord 或者 KAD 中有恶意节点，对有何影响？

下面逐题详细解答。

### Q11. 课堂讨论：如果许多人都搭建 RON，会怎么样？

**解**（先讲 RON 是什么，再推演"人人都建"的后果）：

1. **RON 的机制**：在互联网之上建一个节点全互连的 mesh，每个节点持续测到其他节点的时延/丢包/吞吐，然后决定"直连走"还是"绕一个中间节点走"。
2. **人人建 RON 的后果**：
   - **底层拥塞信号失真**：BGP 只看到"AS 路径跳数"，看不到真实拥塞；RON 都往"看起来好"的路径挤，底层热点被反复叠加；
   - **路由震荡**：一条路径变差，大量 RON 同时切换，切换后又把新路径压垮，来回振荡；
   - **公平性破坏**：能建 RON 的机构（多节点、有余量带宽）占便宜，普通用户被挤；
   - **安全与治理**：RON 绕过底层策略，可能被滥用（放大、匿名攻击），且难以计费与追责。
3. **结论**：RON 用**可扩展性换弹性**，适合小规模、有明确运维主体的场景；大规模部署需要**认证、准入、计费、限速**等约束，否则会破坏互联网的公平与稳定。

### Q12. 课堂练习：设计一个 Sky Computing 的体系架构。

**解**：Sky Computing 的目标是"**像用一朵云一样用多朵云**"。可以按"目标 → 挑战 → 分层架构 → 关键机制"来设计。

**1）目标**：跨云统一调度、跨云数据流动、跨云身份与计费，同时保留各云的独立演进。

**2）挑战**：各云 API 不同、网络不互通、存储不共享、身份不互认、价格与性能各异。

**3）分层架构（六层）**：

| 层 | 作用 | 关键机制 |
| --- | --- | --- |
| 统一接口层 | 对上提供一致的 IaaS/PaaS API | 适配器模式，屏蔽各家 API 差异 |
| 统一调度层 | 按价格/性能/位置放置与迁移 | 全局调度器、跨云弹性、成本优化 |
| 统一网络层 | 打通跨云 VPC | overlay/隧道、就近接入、带宽保障 |
| 统一存储层 | 跨云数据复制与一致性 | 数据放置、缓存、一致性协议 |
| 统一安全层 | 跨云身份、密钥、审计 | 联邦身份（OIDC）、统一策略、密钥托管 |
| 可观测与计费 | 监控、日志、成本分摊 | 跨云指标采集、按需计费 |

**4）关键机制**：

- **抽象**：把"云"抽象成"资源池 + 接口"，上层应用不感知具体云；
- **调度**：按"延迟敏感放近、成本敏感放便宜云"的策略；
- **数据**：热数据就近、冷数据集中，跨云复制保证可用性；
- **安全**：跨云联邦身份，最小权限，审计可追溯。

**5）评价**：难点在**跨云网络**（延迟、带宽、合规）与**数据一致性**；可以先从"同一应用的多云备份/突发扩容"做起，再走向"真正的跨云统一调度"。

### Q13. 问题：如果 Chord 或 KAD 中有恶意节点，会有什么影响？

**解**（先讲攻击面，再讲影响，最后讲防御）：

1. **攻击面**：
   - Chord 的环 + Finger Table、KAD 的 XOR 距离 + K 桶，都依赖"节点 ID 可信、路由信息真实"；
   - 一旦有恶意节点，它可以**伪造 ID、不回包、乱回包、污染数据**。
2. **具体影响**：
   - **路由劫持**：把查询引向自己或同伙，返回错误/伪造数据；
   - **Sybil 攻击**：伪造大量节点 ID，占据环/桶的大片空间，控制查询；
   - **Eclipse 攻击**：用大量假节点"包围"目标，切断它与真实网络的联系；
   - **拒绝服务**：恶意节点不回包、乱回包，拖慢甚至阻塞查询；
   - **数据污染**：在 DHT 中存入错误键值，污染整个网络。
3. **防御**：
   - **节点 ID 绑定身份**（证书/签名），提高 Sybil 成本；
   - **冗余查询**：多路径、多副本交叉验证，少数恶意节点不影响结果；
   - **信誉/黑名单**：记录不良行为，逐步剔除；
   - **数据签名**：查询结果带签名，收到后校验。

## 传输层（一）：可靠传输的五级台阶

**本讲原题（课件原文，按出现顺序）**：

> Q：为什么要在传输层设计可靠的数据传输协议？
>
> RDT2.0 问题：接收方如何检测接收到的数据是否正确？接收方已经知道接收的数据正确与否，那么如何告诉发送方？接收方如果收到了一个错误的数据，如何处理错数据？
>
> RDT2.0 设计有什么缺陷？
>
> Q：Duplicate Packets Problem，Receiver 并不知道当前重发的报文段是由于错误重传还是新的数据报文。
>
> RDT3.0 问题：1）如何检测有数据包丢失？引入什么新的设计机制？2）数据报丢失后如何解决？
>
> 问题：该时间周期如何确定？
>
> Q：序号长度与窗口长度有什么关系？

### Q14. 为什么要在传输层设计可靠的数据传输协议？

**解**：

1. **下层不可靠**：物理链路会因电磁干扰产生**比特错误**；网络层（IP）是"尽力而为"，会**丢包、乱序、重复**，且不保证时延。
2. **上层有需求**：应用需要"准确、不丢、按序"的数据（文件传输、Web、邮件）。
3. **分层设计**：让应用聚焦业务，把"可靠性"作为**通用服务**由传输层统一提供，避免每个应用自己实现一遍。

**答**：因为传输层以下的链路/网络层提供的服务不可靠（如电磁干扰、丢包），而应用需要可靠；传输层通过校验、序号、确认、重传等机制把"不可靠"变成"可靠"，这就是分层设计的意义。

### Q15. RDT2.0 的三个设计问题：如何检测？如何告知？如何处理错误数据？

**解**：

1. **如何检测**：在报文里加**校验和/CRC**，接收方重新计算并与收到的校验和比对，不一致就说明有比特错误。
2. **如何告知**：用**确认反馈**——正确回 **ACK**（positive acknowledgment），错误回 **NAK**（negative acknowledgment）。课件用"接电话听清了说 OK、没听清说再说一遍"来类比。
3. **如何处理**：接收方**丢弃**错误数据；发送方收到 NAK（或超时）后**重传**。RDT2.0 的完整机制就是：**差错检测 + 接收反馈 + 错误重传**。

### Q16. RDT2.0 的设计有什么缺陷？

**解**：

1. **ACK/NAK 本身可能出错或丢失**：如果 ACK 丢了，发送方会重发；如果 ACK 错了，发送方可能误判。此时发送方"直接重发上一个数据报"，但接收方**无法区分**这是"新包"还是"重传的旧包"——产生**重复分组问题**。
2. **停等（stop-and-wait）效率低**：发送方必须等到 ACK/NAK 才能发下一个，链路利用率低。

**答**：缺陷是①确认包本身可能出错，导致重复分组；②停等效率低。前者用**序号**解决（RDT2.1/2.2），后者用**流水线/窗口**解决（GBN/SR）。

### Q17. 什么是 Duplicate Packets Problem？怎么解决？

**解**：

1. **问题**：接收方收到一个报文段，但无法判断它是"发送方因为 ACK 出错而**重传的旧包**"，还是"发送方发来的**新包**"。如果当成新包，就会**重复交付**。
2. **解决**：给报文段加**序号（Sequence Number）**。
3. **RDT2.1**：同时用 **ACK + NAK + 1 位序号**；接收方比较序号，相同就是重传（丢弃），不同就是新包（接收）。
4. **RDT2.2**：只用 **ACK + 序号**，去掉 NAK；收到**重复 ACK** 就说明接收方没正确收到，发送方重传。

**答**：用序号区分"新包/重传包"；RDT2.1 用 ACK+NAK+序号，RDT2.2 用 ACK+序号（重复 ACK 表示出错）。

### Q18. RDT3.0：如何检测数据包丢失？引入什么新机制？丢包后怎么解决？

**解**：

1. **检测丢包**：引入**定时器（Timer）**。发送方发出数据后启动计时，若在超时时间内没收到 ACK，就认为"数据或 ACK 丢了"。
2. **新机制**：定时器 + **超时重传**。
3. **解决**：超时后**重发该数据包**；接收方用序号去重，发送方收到 ACK 后停止计时。
4. **关键洞察**：发送方**不区分**"数据丢了""ACK 丢了""只是延迟大"，一律超时重传——这就是 RDT3.0 的精髓。

**答**：用**定时器**检测超时；超时后**重传**；配合校验和、序号、ACK 构成完整机制。

### Q19. 超时重传的时间周期怎么确定？

**解**：

1. **理论下界**：`RTT + 路由器缓冲 + 分组处理时间`（课件写法：`Min(时间周期) = RTT delay + Router Buffering + packet processing time + etc.`）。
2. **实际做法**：**自适应估计**，用指数加权移动平均（EWMA）跟踪 RTT：

```
EstimatedRTT = (1 − α) × EstimatedRTT + α × SampleRTT      （α = 0.125）
DevRTT       = (1 − β) × DevRTT + β × |SampleRTT − EstimatedRTT|  （β = 0.25）
TimeoutInterval = EstimatedRTT + 4 × DevRTT
```

3. **取大不取小**：周期太小会**误重传**（浪费带宽、制造重复），太大则**反应慢**；所以加 4 倍偏差做安全余量，"likely but not guaranteed"。

**答**：用 `EstimatedRTT + 4×DevRTT` 自适应估计；宁可略大也不能太小。

### Q20. 序号长度与窗口长度有什么关系？

**解**：

1. 设序号用 **k 位**，序号空间为 **2^k**。
2. **GBN**：窗口 `N ≤ 2^k − 1`。
3. **SR**：窗口 `N ≤ 2^(k−1)`，即**不超过序号空间的一半**。
4. **为什么 SR 要一半**：接收方要能区分"新包"和"重传的旧包"。若窗口超过一半，序号绕一圈后，同一个序号既可能是新包也可能是旧包，接收方无法判断，会**重复交付或错判**。

**答**：GBN 窗口 ≤ 2^k − 1；SR 窗口 ≤ 2^(k−1)（序号空间的一半）。

## 传输层（二）：TCP 拥塞控制的三个核心问题

**本讲原题（课件原文）**：

> 第一个问题：TCP 发送方如何限制向其连接发送流量的速率？
>
> 第二个问题：TCP 发送方如何感知自身和目标之间的路径上存在拥塞？
>
> 第三个问题：发送方应该使用什么算法来更改其发送速率？
>
> 进一步思考：TCP Reno 对拥塞窗口的 AIMD 机制是探测最优发送速率的最佳方法吗？

### Q21. 第一个问题：TCP 发送方如何限制向连接发送流量的速率？

**解**：

1. TCP 维护一个**拥塞窗口 cwnd**（congestion window），表示"允许在途、尚未确认的数据量上限"。
2. 发送方必须满足：

```
LastByteSent − LastByteAcked ≤ min(cwnd, rwnd)
```

3. 在假设接收窗口足够大（忽略 rwnd）时，发送速率约为：

```
发送速率 ≈ cwnd / RTT
```

4. 所以**调整 cwnd 就能控制速率**：cwnd 大就发得快，cwnd 小就发得慢。

**答**：用 cwnd 限制未确认数据量，速率 ≈ cwnd/RTT；通过调整 cwnd 来控制发送速率。

### Q22. 第二个问题：TCP 发送方如何感知路径上存在拥塞？

**解**：

1. **丢包信号**：**超时**或收到 **3 个重复 ACK**，就认为路径拥塞（包丢了）。
2. **自时钟**：TCP 用 ACK 到达来"驱动"窗口增长——ACK 来得快，窗口涨得快；ACK 来得慢，窗口涨得慢。所以 TCP 被称为**自时钟（self-clocking）**。

**答**：通过超时或 3 个重复 ACK 感知丢包/拥塞；ACK 的节奏驱动窗口增长（自时钟）。

### Q23. 第三个问题：发送方应该用什么算法更改发送速率？

**解**：

1. 用**拥塞控制算法**：慢启动（slow start）、拥塞避免（congestion avoidance）、快速恢复（fast recovery）。
2. **三条指导原则**：
   - **丢包 = 拥塞** → 丢包时**降速**（乘性减）；
   - **ACK = 网络在交付** → 收到新 ACK 时**提速**（加性增）；
   - **带宽探测** → 不断试探更高速率，直到丢包为止。
3. 这套"加性增、乘性减"（AIMD）就是 TCP 拥塞控制的核心。

**答**：用慢启动/拥塞避免/快速恢复，遵循"丢包降速、ACK 提速、带宽探测"三原则。

### Q24. 进一步思考：TCP Reno 的 AIMD 是探测最优发送速率的最佳方法吗？

**解**：

1. **不是**。Reno 的 AIMD 每次丢包都把 cwnd 减半，然后用"每 RTT 加 1 MSS"的线性方式慢慢爬回来。
2. **问题**：丢包发生时，链路容量往往**没有明显变化**；AIMD 却要"退一大步、慢慢爬"，**过于保守**，损害带宽利用率。
3. **改进**：应该**更快恢复到丢包前的速率**。**CUBIC** 用三次函数代替线性增长，快速逼近丢包前的窗口 Wmax，在高带宽长时延链路上表现更好。
4. **演进线**：TCP Tahoe → Reno → NewReno → CUBIC。

**答**：不是；AIMD 过于保守，应更快恢复到丢包前速率——这就是 CUBIC 的思路。

## 网络连接：划分子网的三道例题

**本讲原题（课件原文）**：

> **【例1】** 已知 IP 地址 141.14.72.24，子网掩码 255.255.192.0。求：(a) 点分十进制 IP；(b) IP 第 3 字节的二进制；(c) 子网掩码；(d) IP 与掩码逐位相与；(e) 网络地址。
>
> **【例2】** 在上例中，若子网掩码改为 255.255.224.0，重做 (a)～(e)。
>
> **【例】** 现有地址 203.33.18.0，需 13 个子网、每个子网 10 个主机。求子网掩码与各子网地址范围。

### Q25.【例1】IP 141.14.72.24，掩码 255.255.192.0，求网络地址。

**解**（按课件的 (a)～(e) 五步）：

1. **(a) 点分十进制 IP**：`141.14.72.24`。
2. **(b) 第 3 字节的二进制**：72 = 64 + 8 = **0100 1000**。
3. **(c) 子网掩码**：255.255.192.0 → 第 3 字节 192 = **1100 0000**。
4. **(d) 逐位相与**：

```
  0100 1000   （72）
AND 1100 0000   （192）
=   0100 0000   （64）
```

5. **(e) 网络地址**：141.14.**64**.0。

**答**：**141.14.64.0**。

### Q26.【例2】掩码改为 255.255.224.0，求网络地址。

**解**：

1. **(a)** IP 仍是 `141.14.72.24`。
2. **(b)** 第 3 字节 72 = **0100 1000**。
3. **(c)** 掩码 255.255.224.0 → 第 3 字节 224 = **1110 0000**。
4. **(d) 逐位相与**：

```
  0100 1000   （72）
AND 1110 0000   （224）
=   0100 0000   （64）
```

5. **(e) 网络地址**：141.14.**64**.0。

**答**：网络地址仍是 **141.14.64.0**。但要注意：**不同掩码可能得到相同网络地址，效果却不同**——/18（255.255.192.0）和 /19（255.255.224.0）可划分的子网数、每个子网的最大主机数都不一样。这正是"必须同时给出 IP 和掩码"的原因。

### Q27.【例】203.33.18.0 划 13 个子网、每子网 10 台主机，怎么划？

**解**（按课件的四步）：

1. **第 1 步：确定默认掩码和主机号位数**：203.33.18.0 是 **C 类**地址，默认掩码 255.255.255.0，主机号为最后 1 字节（**8 位**）。
2. **第 2 步：确定借几位**：需要 13 个子网 → `2^n ≥ 13` → **n = 4**（2^4 = 16 ≥ 13）；剩余主机位 h = 8 − 4 = **4**，每个子网可用主机数 `2^4 − 2 = 14 ≥ 10`，满足。
3. **第 3 步：写出子网掩码**：前 24 + 4 = **28 位**为 1 →

```
11111111.11111111.11111111.11110000 = 255.255.255.240（/28）
```

4. **第 4 步：确定每个子网的地址范围**（块大小 = 256 − 240 = **16**）：

| 子网 | 子网号 | 地址范围 | 可用主机范围 |
| --- | --- | --- | --- |
| 1 | 0000 | 203.33.18.0 ~ 15 | .1 ~ .14 |
| 2 | 0001 | 203.33.18.16 ~ 31 | .17 ~ .30 |
| 3 | 0010 | 203.33.18.32 ~ 47 | .33 ~ .46 |
| 4 | 0011 | 203.33.18.48 ~ 63 | .49 ~ .62 |
| 5 | 0100 | 203.33.18.64 ~ 79 | .65 ~ .78 |
| 6 | 0101 | 203.33.18.80 ~ 95 | .81 ~ .94 |
| 7 | 0110 | 203.33.18.96 ~ 111 | .97 ~ .110 |
| 8 | 0111 | 203.33.18.112 ~ 127 | .113 ~ .126 |
| 9 | 1000 | 203.33.18.128 ~ 143 | .129 ~ .142 |
| 10 | 1001 | 203.33.18.144 ~ 159 | .145 ~ .158 |
| 11 | 1010 | 203.33.18.160 ~ 175 | .161 ~ .174 |
| 12 | 1011 | 203.33.18.176 ~ 191 | .177 ~ .190 |
| 13 | 1100 | 203.33.18.192 ~ 207 | .193 ~ .206 |
| 14 | 1101 | 203.33.18.208 ~ 223 | .209 ~ .222 |
| 15 | 1110 | 203.33.18.224 ~ 239 | .225 ~ .238 |
| 16 | 1111 | 203.33.18.240 ~ 255 | .241 ~ .254 |

**答**：掩码 **255.255.255.240（/28）**，共 **16 个子网**，每个子网 **14 台**可用主机；13 个子网的需求用其中任意 13 个即可。

> 借位口诀：**子网数看借几位（2^n），主机数看剩几位（2^h − 2）**；先满足子网数，再验证主机数，两者都满足才停。

## 网络安全（一）：从体系结构看安全

**本讲原题（课件原文）**：

> **课堂讨论 1**：
> 问题1：从 IPv4 到 IPv6 最大的改变是地址长度增加，请分析这一改变属于体系结构上的还是功能上的？
> 问题2：请分析防火墙作为一个网络功能，在利益一致性、传递和参数化三个维度上的特征。
>
> **课堂讨论 2**：
> 问题1："木马"程序与最初的互联网安全假设"通信只发生在彼此互信的各方之间"有何关联？
> 问题2：请分析"网络负责保证通信只发生在彼此互信的各方之间"这一目标与端到端原则的关系。
>
> **课堂讨论 3**：
> 问题1：请分析保护通信和保护主机之间存在哪些冲突？
> 问题2：请给以下互联网安全目标排出一个优先级：保护主机、保护网络、保护通信、防御 DDoS。
>
> **开放问题**：网络体系结构如何针对拜占庭将军问题设计？
>
> **激励问题**：路由器为什么为远端用户提供过滤服务（如 DDoS 清洗）？

### Q28. 课堂讨论 1：问题1：IPv6 地址长度增加，属于体系结构上的还是功能上的改变？

**答题思路**：先区分"体系结构"和"功能"——体系结构是**设计原则与表达力**（能表达什么、地址语义、可扩展性），功能是**具体机制**（怎么实现某个特性）。

**要点**：

1. 体系结构定义的是"**表达力**"：地址格式决定了网络能表达什么、能支持什么样的编址与路由。
2. IPv6 把地址从 32 位扩到 128 位，直接改变了**命名/寻址的语义与可聚合层次**，进而影响路由、移动性、安全、自动配置等设计空间。
3. 它不是简单"多加几个字节"，而是**改变了互联网的表达力**（例如可以给每个设备一个全球地址、可以做层次化聚合）。

**结论**：**更偏体系结构层面**（改变了表达力与设计空间），实现上是功能增强。答题时点出"表达力"这个词，会显得理解更深。

### Q29. 课堂讨论 1：问题2：防火墙在利益一致性、传递、参数化三个维度上的特征。

**答题思路**：先回忆课件"表达力在 PHB 上的三个维度"：①利益是否一致；②包如何到达实现 PHB 的节点（传递方式）；③包作为 PHB 的参数（参数化方式）。

**要点**：

| 维度 | 防火墙的特征 |
| --- | --- |
| 利益一致性 | 与**内部用户利益一致**（保护内网），与**外部攻击者利益对立**（要拦截恶意流量） |
| 传递方式 | **拓扑的/强迫的**——流量进出内网必须经过边界防火墙；也可以是"有意的"（策略指定） |
| 参数化方式 | 主要**显式**（用 IP、端口、协议等首部字段）；做 DPI 时也用**隐式**（把载荷当参数） |

**结论**：防火墙是"**与内部一致、与外部对立**"的 PHB，靠**拓扑强制**让流量经过，用**首部字段（显式）或载荷（隐式）**做判断。

### Q30. 课堂讨论 2：问题1："木马"与"通信只发生在彼此互信的各方之间"的假设有何关联？

**答题思路**：先复述假设，再说明木马如何击穿它，最后给结论。

**要点**：

1. 最初的互联网假设：**通信双方是互相信任的**，网络是"透明管道"。
2. 木马**伪装成可信程序**（邮件附件、下载软件、破解工具），用户主动运行后，它从**内部**发起外连或接收指令——通信双方表面上"互信"，实际一方已被控制。
3. 结论：木马说明"**基于互信的安全模型不成立**"，必须靠**认证、最小权限、隔离、行为检测**来补；安全不能只靠"假设对方是好人"。

### Q31. 课堂讨论 2：问题2："网络负责保证通信只发生在互信各方之间"与端到端原则的关系。

**答题思路**：先讲端到端原则，再讲这个目标为什么与它冲突，最后给折中。

**要点**：

1. **端到端原则**：复杂功能（含安全、可靠性）应放在**端系统**，网络只负责转发，保持简单。
2. "网络保证互信"要求**网络中间节点**做认证、过滤、访问控制——违反端到端原则，且难以扩展（网络要理解每个应用、维护海量状态）。
3. 折中：**网络提供基础隔离与可达性**（如 VLAN、防火墙、ACL），**信任判断交给端系统与应用**（TLS、认证、授权）。

**结论**：两者**冲突**；合理的分工是"网络做粗粒度隔离，端系统做细粒度信任判断"。

### Q32. 课堂讨论 3：问题1：保护通信和保护主机之间存在哪些冲突？

**答题思路**：从"可见性""可用性""成本"三个角度展开。

**要点**：

1. **可见性冲突**：保护通信（加密、匿名）→ 网络/中间设备**看不到内容**，难以识别针对主机的恶意流量；保护主机（DPI、IDS、过滤）→ 需要**看内容**，又损害通信机密性与隐私。
2. **可用性冲突**：强加密可能被用来隐藏攻击；强过滤可能误伤正常业务。
3. **治理冲突**：端到端加密让"网络侧安全"失效，安全责任转移到端系统。

**结论**：两者在"**是否让网络看到内容**"上根本冲突；实践中用"端系统加密 + 端点检测 + 元数据防护"来平衡。

### Q33. 课堂讨论 3：问题2：给四个安全目标排优先级。

**答题思路**：开放题，给排序 + 理由 + 场景修正。

**要点**（一个常见排序）：

```
保护主机  >  保护通信  >  防御 DDoS  >  保护网络
```

**理由**：

1. **主机是攻击的最终目标**，也是被控后发起攻击的跳板，所以排第一；
2. **通信安全直接关系用户隐私与数据**，排第二；
3. **DDoS 主要影响可用性**，可用冗余/清洗缓解，排第三；
4. **"保护网络"更多是手段而非目的**，且与开放性有张力，排最后。

**修正**：关键基础设施场景可把"保护网络"提前；开放互联网场景则更看重"保护通信"。

### Q34. 开放问题：网络体系结构如何针对拜占庭将军问题设计？

**答题思路**：先解释拜占庭问题，再从"冗余、验证、共识、激励"四个层面给设计。

**要点**：

1. **拜占庭问题**：部分节点可能作恶或故障，其余节点仍要达成一致（终止性、一致性、有效性）。
2. **冗余与多路径**：用多条独立路径/多个副本交叉验证，降低单点作恶影响。
3. **可验证的身份与签名**：让"谁说的"可验证（PKI、路由签名），提高作恶成本。
4. **共识与投票**：在控制平面（路由、DNS 根）引入拜占庭容错共识（如 PBFT 类）。
5. **激励与惩罚**：抵押、罚没、信誉，让作恶在经济上不划算。

**难点**：现有互联网的路由/DNS 是"信任 + 协作"模型，不是拜占庭容错模型；真正落地需要全局部署，成本和激励都是障碍。

### Q35. 激励问题：路由器为什么愿意为远端用户提供过滤服务？

**答题思路**：从"利己、商业、联盟、监管"四个角度解释激励。

**要点**：

1. **利己**：过滤能保护**自己的客户和链路**，减少拥塞与投诉。
2. **商业**：清洗/过滤可以**卖服务**（CDN、清洗中心是生意）。
3. **联盟**：参与协同防御能换取**对等互通、信誉、政策支持**。
4. **监管**：法规/合规要求运营商协助防护。

**问题**：若只付出没回报，会出现"**搭便车**"，所以需要**计费、联盟、监管**来维持激励。

### Q36. 上不去网或上不去某个网站，怎么判断是否由 DNS 引起？

**解题思路**：把"网络连通性"和"域名解析"分开测，逐步缩小范围。

**解**：

1. **测基础连通性**：`ping 8.8.8.8`（或网关）。通则说明 IP 层网络没问题；不通则是本地/接入网问题，与 DNS 无关。
2. **测目标 IP**：先 `nslookup 域名` 拿到 IP（或从别处查），再 `ping 该IP`。**IP 通、域名不通 → DNS 问题**；IP 也不通 → 网络/服务器问题。
3. **查解析**：`nslookup 域名`、`dig 域名`，看是否返回错误、超时、或可疑地址。
4. **换 DNS 对比**：`dig @8.8.8.8 域名` 与 `dig @114.114.114.114 域名`，结果不一致说明某个解析器有问题。
5. **排除本地因素**：检查 hosts 文件、本地 DNS 配置、浏览器/系统缓存。
6. **逐级定位**：`dig +trace 域名`，看是根、TLD 还是权威服务器出错。

**答**：先 ping IP 确认网络，再查域名解析、换公共 DNS 对比；"IP 通、域名不通"基本就是 DNS 故障。

### Q37. 用 CIA 分析 DNS 攻击；如何用非密码学手段防御？

**解题思路**：先明确"上述攻击"指缓存下毒/名字链/Kaminsky/反射放大，再逐属性分析，最后给非密码学防御。

**解**：

1. **完整性（Integrity）**：**被破坏**——攻击者让解析器缓存了错误的"域名 → IP"映射（缓存下毒、Kaminsky）。
2. **可用性（Availability）**：**被破坏**——DDoS/反射放大让 DNS 服务不可用（2009 暴风、2016 Dyn）。
3. **机密性（Confidentiality）**：影响较小（DNS 查询本身不加密，可能被窃听，但不是这类攻击的主目标）。

**非密码学防御**：

- **源端口随机化**：把 16 位事务 ID + 16 位源端口变成 32 位熵，猜测难度从 2^16 升到 2^32；
- **0x20 编码**：随机改变查询名的大小写，增加伪造难度；
- **限制递归查询**：只对可信客户端开放递归，减少被利用；
- **缩短缓存 TTL**、**响应速率限制（RRL）**；
- **Anycast 分散** + **流量清洗**；
- **网络监测与异常告警**。

**答**：主要破坏完整性与可用性；非密码学防御靠端口随机化、0x20、限制递归、RRL、Anycast、监测。

### Q38. 如何安全地获得公钥？

**解题思路**：核心是"不直接信任公钥，而是信任给公钥签名的人"，即证书 + CA + PKI。

**解**：

1. **CA（证书权威）** 用自己的私钥给"**公钥 + 身份信息**"签名，生成**数字证书**。
2. 通信方拿到证书后，用 **CA 的公钥**验证签名，确认"这把公钥确实属于这个身份"。
3. CA 的公钥通过**信任锚**（预置在浏览器/系统）和**证书链**逐级验证。
4. 这样只需安全发布"信任锚"，就能安全发布所有其他公钥。

**答**：用数字证书 + CA + PKI，通过信任锚和证书链验证公钥归属；本质是"信任签名者，而不是信任公钥本身"。

### Q39. 列出从根 KSK 到 www.abc.com 的 A 记录的完整信任链。

**解题思路**：按"父区 DS 指向子区 KSK，子区 KSK 签 ZSK，ZSK 签数据"的顺序写。

**解**：

```
根 KSK（信任锚）
 → 根 KSK 签名根 ZSK（DNSKEY + RRSIG）
 → 根 ZSK 签名 .com 的 DS（RRSIG(DS)）
 → .com 的 DS 指向 .com 的 KSK
 → .com 的 KSK 签名 .com 的 ZSK
 → .com 的 ZSK 签名 abc.com 的 DS
 → abc.com 的 DS 指向 abc.com 的 KSK
 → abc.com 的 KSK 签名 abc.com 的 ZSK
 → abc.com 的 ZSK 对 www.abc.com 的 A 记录生成 RRSIG
 → 解析器逐级验证，最终确认 A 记录真实
```

**答**：`根 KSK → 根 ZSK → DS(.com) → .com KSK → .com ZSK → DS(abc.com) → abc.com KSK → ZSK → RRSIG(A)`。

### Q40. DNSSEC 为什么不保护 stub resolver 与递归解析器之间的通信？

**解题思路**：先明确 DNSSEC 的保护范围，再解释"最后一公里"为何不在其中。

**解**：

1. DNSSEC 保护的是"**递归解析器 ↔ 权威服务器**"这一段的数据真实性与完整性。
2. 它假设 **stub resolver 信任本地递归解析器**（两者通常在同一主机或同一可信网络）。
3. stub 到递归这一段属于"最后一公里"，DNSSEC 的签名链覆盖不到；要保护它，需要 **DoH/DoT** 等通道加密，或本地信任配置。

**答**：DNSSEC 只覆盖"递归↔权威"，stub 到递归是本地/接入段，靠本地信任；要保护需 DoH/DoT。

### Q41. 从 AS0 到 AS1–AS9，哪些路径是 valley-free 的？

**题图说明**（课件第 60 页）：中心为 **AS0**；上方一组经 **C2P** 连接 AS1、AS2、AS3；右侧一组经 **P2P** 连接 AS4、AS5、AS6；下方一组经 **P2C** 连接 AS7、AS8、AS9。图中 **○ 表示 valley-free，✗ 表示不满足**。组内每条边的类型（C2P/P2P/P2C）见图。

**解题思路**：valley-free 的判据是——一条 AS 路径中，**在 P2C 或 P2P 之后，不能再出现 C2P 或 P2P**；只允许"**上坡（C2P）→ 对等（P2P）→ 下坡（P2C）**"的形状。

**解**：把每条路径写成"第一跳类型 + 第二跳类型"：

| 目的 | 路径形状 | 是否 valley-free |
| --- | --- | --- |
| AS1 | C2P → C2P | ✓（一路向上） |
| AS2 | C2P → P2P | ✓（上坡后对等） |
| AS3 | C2P → P2C | ✓（上坡后下坡） |
| AS4 | P2P → C2P | ✗（对等后又上坡） |
| AS5 | P2P → P2P | ✗（对等后还对等） |
| AS6 | P2P → P2C | ✓（对等后下坡） |
| AS7 | P2C → C2P | ✗（下坡后又上坡，形成"谷"） |
| AS8 | P2C → P2P | ✗（下坡后又对等） |
| AS9 | P2C → P2C | ✓（一路向下） |

**答**：valley-free 的目的地是 **AS1、AS2、AS3、AS6、AS9**；**AS4、AS5、AS7、AS8** 不满足（与图中 ○/✗ 标记一致）。

### Q42. AS6 被恶意控制、劫持 AS2 的前缀：哪些 AS 受影响？如何非密码学检测？

**题图说明**（课件第 71 页）：AS2 拥有 `10.0.0.0/16`；AS6 也宣告 `10.0.0.0/16`（橙色，恶意）。拓扑：AS1 ↔ AS2；AS3 → AS1；AS4 → AS1；AS3 ↔ AS4；AS4 ↔ AS5；AS7 → AS4；AS7 → AS5；AS6 → AS3。

**解题思路**：从 AS6 出发，沿"谁会把这条更优路由传播出去、谁会在策略上选它"逐跳推演。

**解**：

1. **AS6 → AS3**：AS3 从客户 AS6 学到劫持路由，客户路由优先，**AS3 改用劫持路由**。
2. **AS3 → AS1**：AS1 从客户 AS3 学到劫持路由，同时从对等 AS2 学到合法路由；**客户优先**，AS1 选劫持路由。
3. **AS3 → AS4**：AS4 从对等 AS3 学到劫持路由，从提供商 AS1 学到合法路由；**对等优先于提供商**，AS4 选劫持路由。
4. **AS4 → AS5**：AS5 从对等 AS4 学到劫持路由，**AS5 受影响**。
5. **AS4/AS5 → AS7**：AS7 从提供商 AS4/AS5 学到劫持路由，**AS7 受影响**。
6. **AS2**：它是前缀的**合法起源**，不会被劫持路由影响（起源自身始终有效）。

**受影响**：**AS1、AS3、AS4、AS5、AS7**；AS2 不受影响（起源），AS6 是攻击者。

**非密码学检测**：

- **路由监测**：BGPmon/RouteViews 多 vantage point 看"某前缀的起源 AS 变了"；
- **起源一致性**：`10.0.0.0/16` 历史上一直由 AS2 起源，突然出现 AS6 即异常；
- **路径异常**：路径里出现不该出现的低层 AS；
- **前缀过滤**：AS6 不属于该前缀的合法持有者，应被过滤；
- **looking glass / traceroute**：看实际转发路径是否改变。

### Q43. AS4 被恶意控制，如何对 AS5 的前缀实施"前缀窃听"？如何非密码学防御？

**题图说明**（课件第 80 页）：AS5 拥有 `10.0.0.0/16`；AS4 被恶意控制（深色）。拓扑：AS1 ↔ AS2；AS3 → AS1；AS4 → AS1；AS3 ↔ AS4；AS4 ↔ AS5；AS7 → AS4；AS7 → AS5；AS6 → AS3。

**解题思路**：窃听 = 让流量**经过攻击者**，再转发给受害者；关键是"声明受害者的前缀、并让路径看起来更优"。

**解**：

1. **宣告**：AS4 向它的邻居（AS1、AS3、AS7）宣告 AS5 的前缀 `10.0.0.0/16`（或拆成更具体的子前缀）。
2. **吸引流量**：AS4 与 AS5 是对等，本来就在 AS5 的"上游"；它的宣告让 AS1/AS3/AS7 以为"经 AS4 更近"，把去往 AS5 的流量发给 AS4。
3. **窃听 + 转发**：AS4 记录/复制流量，再**转发给 AS5**，让受害者"看起来正常"，不易察觉。
4. **非对称**：只窃听**去程**（到 AS5 的流量），回程未必经过 AS4，所以是"前缀窃听"而非完整中间人。

**非密码学防御**：

- **前缀过滤**：AS1/AS3/AS7 拒绝来自 AS4 的"不属于 AS4"的前缀宣告；
- **路由监测**：监测"某前缀突然多了一个起源/路径异常"；
- **RPKI/ROA**（密码学，但可提一句）：验证起源；
- **加密**：TLS 让窃听到的内容不可读；
- **traceroute 验证**：看实际路径是否绕经 AS4。

### Q44. RPKI 的 ROA 中"最大前缀长度（maxLength）"有什么用？

**解题思路**：从"防子前缀劫持、防路由泄露、验证严格性"三个角度回答。

**解**：

1. **防子前缀劫持**：攻击者常把 `/16` 拆成多个 `/24` 做"更精确"的劫持；maxLength 限制"最长只能宣告到 /X"，拆得更细就判 **Invalid**。
2. **防路由泄露**：防止 AS 宣告过长前缀抢占流量。
3. **验证更严格**：超出 maxLength 的宣告被判 Invalid，从而被过滤或降权。

**答**：限制该起源 AS 可宣告的最长前缀，防止"拆细前缀"的精确劫持与过长前缀的路由泄露。

### Q45. 为什么当年 IP 被成功部署，而这些未来互联网体系结构没有部署？

**解题思路**：从"技术、经济、生态、治理"四个层面比较 IP 与未来架构的部署条件。

**解**：

1. **技术层面**：IP **简单、可增量部署**——一个网络先上 IP 不影响别人；未来架构（NDN、LISP 等）往往要求**全局替换**或大范围改造。
2. **兼容性**：IP 只要求"能传包"，底下什么技术都行（IP over everything）；NDN 要求全网理解"名字"，兼容成本高。
3. **经济与激励**：IP 有 **Web 等杀手应用**牵引，部署者能获益；未来架构缺乏同等量级的应用，且改动大、成本高。
4. **治理与协调**：IP 不改现有设备、不触动运营商利益；未来架构需要**多方协调**（运营商、厂商、内容商），难以达成一致。

**答**：IP 胜在"简单、可增量、兼容异构、有应用牵引、经济可行"；未来架构输在"改动大、需全局部署、缺激励、协调难"。

### Q46. 在前面介绍的几种体系中，你偏好哪一个？为什么？

**解题思路**：开放题，给"偏好 + 两三条理由 + 承认缺点"。

**解**（示例，可换成你自己的偏好）：

> 我偏好 **NDN**。理由：①它把"内容"而不是"地址"作为中心，天生支持缓存、多播和移动；②数据自带签名，安全内建，不依赖连接；③对视频/内容分发这类主流流量更自然。缺点也明显：命名与路由可扩展性、PIT 状态开销、与 IP 的兼容和部署激励。

若更看重"能落地"，也可以偏好 **LISP**：不改主机、可增量部署，能缓解路由表膨胀。

**答**：给偏好 + 理由 + 缺点即可；关键是"有理有据"，不要只给结论。

### Q47. 与 IP 相比，NDN 的优点和缺点是什么？

**解题思路**：按"通信模型、缓存、移动、安全、可扩展性、部署"逐项对比。

**解**：

| 维度 | NDN 相对 IP |
| --- | --- |
| 通信模型 | 从"主机到主机"变为"**数据获取**"，按名字取数据 |
| 内容分发 | **天生支持**多播、网内缓存，适合视频/大文件 |
| 移动性 | 消费者换地址不影响取数据（按名字，不绑地址） |
| 安全 | **数据自带签名**，保护内容本身而非连接 |
| 抗 DDoS | **有状态转发**（PIT）限制未满足请求，缓解洪泛 |
| 可扩展性 | 名字空间无穷大，**命名与路由可扩展性**是难题 |
| 状态开销 | 路由器要维护 **PIT**，状态量大 |
| 缓存一致性 | 网内缓存带来**一致性**问题 |
| 部署 | 与 IP **不兼容**，全局部署难、缺激励 |

**答**：优点——内容分发/缓存/移动/安全内建/抗 DDoS；缺点——命名与路由可扩展性、PIT 开销、缓存一致性、部署难。

### Q48. NDN 可能适用于什么场景？

**解题思路**：从"以内容为中心、移动性强、网络条件差"三类场景展开。

**解**：

1. **内容分发**：视频、大文件、软件更新、CDN/边缘缓存。
2. **移动/车联网/IoT**：消费者移动不影响取数据；按数据名字取读数。
3. **断开/灾难环境（DTN）**：网络时断时续，靠缓存和"取数据"模式工作。
4. **需要内容级安全**：数据签名，适合证书、软件分发。

**答**：内容分发、移动/车联网/IoT、DTN/灾难环境、内容级安全场景。

### Q49. NDN 与 DNS 相比，有什么共同点？

**解题思路**：先找共同点（名字解析、层次命名），再讲区别。

**解**：

1. **共同点**：都是"**名字 → 位置/数据**"的解析系统；都用**层次化命名**（`/edu/hit/...` 对 `www.hit.edu.cn`）；都需要"解析/映射"这一步。
2. **区别**：DNS 只把域名解析成**服务器 IP**，然后还要用 IP 建连接；NDN **直接用内容名字做路由和转发**，名字本身就是通信的"地址"。

**答**：共同点是"层次化名字 + 解析/映射"；区别是 DNS 解析到 IP，NDN 用名字直接路由取数据。

### Q50. 除了内容分发，NDN 还适用于什么其他类的应用场景？

**解题思路**：从"以数据为中心、对位置不敏感"的应用展开。

**解**：

1. **物联网/传感网**：按数据名字取读数，不关心是哪台设备。
2. **移动/车载网络**：消费者移动不影响取数据。
3. **边缘/网内计算**：就近缓存与复用。
4. **命名数据的安全分发**：数据自带签名，适合软件更新、证书分发。
5. **DTN/断开环境**：靠缓存与"取数据"模式。

**答**：IoT/传感网、移动/车载、边缘缓存、安全数据分发、DTN。

### Q51. "功成不必在我"：NDN 思想与当前互联网哪些知识和挑战有关联？

**解题思路**：找出 NDN 思想在现有技术中的"局部实现"，说明它不必"替换 IP"也能发挥作用。

**解**：

1. **CDN/边缘缓存**：就是"把内容放到离用户近的地方"，与 NDN 的网内缓存同源。
2. **DNS**：名字解析的先驱。
3. **组播/Anycast**：一对多、就近响应。
4. **内容寻址存储（如 IPFS）**：按内容哈希寻址。
5. **DTN/信息中心安全**：断连环境与数据级安全。

**结论**：NDN 不一定以"替换 IP"的方式落地，但它的思想会以"增量"方式渗入 CDN、边缘计算、IoT 等系统——这正是"功成不必在我"。

**答**：与 CDN、DNS、组播/Anycast、内容寻址、DTN 等关联；NDN 思想可"增量"用于这些系统，不必整体替换 IP。

## 其余课件说明：SDN、算力网、无线移动

这三讲（《软件驱动网络》、未来网-算力网、第 7 章无线移动）以概念与技术介绍为主，**课件中没有面向学生的课堂讨论题、练习题或例题**。为保持"题目全集"的完整性，此处说明各讲的可考点，方便你对照复习。

### 软件驱动网络（SDN/NFV）

- **核心概念**：数据面与控制面分离、逻辑集中的控制器、南向接口（OpenFlow）、流表 `<Match, Action>`、P4 可编程数据面、NFV 把中间盒子软件化。
- 常考简答：SDN 与传统网络的区别、OpenFlow 流表结构、P4 与 OpenFlow 的差异、NFV 的挑战（性能、隔离、状态迁移、服务链编排）。

### 未来网-算力网

- **核心概念**：Scale-Up（片间）/ Scale-Out（机间）/ Scale-Across（算间）三层；RDMA、无损网络（PFC/ECN/DCQCN）、IB vs RoCEv2 vs UEC、WRDMA。
- 常考简答：算力网与 IP 的差异（确定性 vs 尽力而为）、RDMA 为什么快、无损网络怎么实现。

### 第 7 章 无线移动网络

- **核心概念**：无线链路四问题（衰减、多径、干扰、隐藏终端）、802.11 的 CSMA/CA 与 RTS/CTS、WPAN（蓝牙/ZigBee/UWB）、4G LTE 网元（UE/eNB/S-GW/P-GW/MME/HSS）、漫游与切换（间接 vs 直接路由）、5G 三大场景与关键技术、6G 展望。
- 常考简答：CSMA/CA 与 CSMA/CD 的区别、隐藏终端怎么解决、间接路由的三角路由问题、切换为什么要"先转发后切换"。
